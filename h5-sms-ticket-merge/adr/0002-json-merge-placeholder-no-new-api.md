# 数据契约用旧 JSON 拼盘占位，不新调接口

H5 模版的数据来自既有「订单小票数据模型」与「交易小票」JSON 文档字段拼在同一份上下文里。前端不调接口；先用 Demo JSON 占位验收。不在本期强制后端出新聚合 DTO。

## 为什么

grill-me 锁定：两份飞书 JSON 文档做占位即可。拼盘改动最小、字段名与旧 FTL 生态一致，后端以后最好接。先上新 DTO 会堵在联调，拖住模版与样板间交付。

## 关键权衡（被否决的备选）

- **A：后端新做短信 H5 专用聚合 DTO**：长期更干净，本期不做硬依赖；可后续迭代。
- **C：前端调两个接口自己拼**：被否决。本期前端只交模版。
- **只绑订单 JSON、完全忽略交易 JSON**：支付区可用订单 `tradeInfo`，但拼盘仍保留交易侧字段供后端扩展，模版选择不渲染即可。

## 后果

- Demo 为拼盘：`merchantInfo`/`mealInfo`/`orderAmountInfo`/`tradeInfo` + 可选 `transInfo`/`cardDetail`/`amountInfo`。
- 新增弹层占位 `taxFeeDetailInfo`（旧文档可能没有），后端后续灌数。
- 模版需容忍字段缺失（`#if`），不能假设两套 JSON 每次都齐。
