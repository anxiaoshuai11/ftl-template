# FTL 小票自测

小票模版的 bug 有个共同特点：**要等真数据渲染那一刻才炸**。某个 `#if` 少判一层空值、某条数据的
`content` 数组短一位，本地看着没事，上生产直接 500。本 skill 在不启动 FreeMarker 引擎的前提下，
用静态分析 + 逐数据行推演把这类问题提前抓出来，并给出一份可以贴进 MR 的自测报告。

## 何时执行

满足任一条件即执行：

- 用户给了 `.ftl` + `.json`，要求自测 / 跑用例 / 出测试结果
- 新建或修改了小票模版，准备提 MR
- 需要回答「这份数据覆盖了模版的哪些分支、还缺哪些用例」

**不要**只改完 FTL 就说「应该没问题」，必须跑出报告再下结论。

## 三个入口

### 单份数据自测

```bash
node ftl-selftest/run-selftest.mjs <模版.ftl> <数据.json> [报告输出路径]
```

产出 `<模版名>.selftest.md`。退出码 0 = 无错误级问题，1 = 有错误，可直接接 CI。

### 场景套件批量自测（推荐）

```bash
node ftl-selftest/run-suite.mjs <模版.ftl> [场景定义.json]
```

按 `ftl-selftest/scenarios.json` 从一份基线数据派生多组场景，一次跑完，产出
`<模版名>.selftest-suite.md`，含「场景 × 结论」总表和整套用例的合并覆盖率。

### 改动前后回归对比（改现有模版时必跑）

```bash
node ftl-selftest/run-regression.mjs <模版.ftl> <数据.json> [基线ref] [报告输出路径]
```

从 git 取出基线版本（默认 `HEAD`，即改动前的样子），与工作区版本跑同一份数据，
产出 `<模版名>.regression.md`，**只列差异**：本次引入的问题、本次消除的问题、新增的顶层分支。
退出码 0 = 没引入新问题。

报告默认写在模版同级目录，而模版通常就在目标仓库里，会污染人家的工作区。
所以第四个参数请显式指到仓库外，例如 `/tmp/xxx.regression.md`。

改现有模版时，「改完还剩几个问题」没有意义，「哪些问题是这次改出来的」才有意义——
老模版本来就带着的告警不该拦住你，你新写出来的空值风险必须拦住你。

问题指纹按内容比对而非行号，代码整体位移不会产生误报。新增模版没有基线版本，
脚本会提示改用 `run-suite.mjs`。

## 报告怎么读

| 章节 | 说明 | 怎么处理 |
|------|------|----------|
| 问题清单 | 错误 / 告警两级 | **错误必须改**；告警要逐条确认是不是误报 |
| 顶层分区用例矩阵 | 决定「哪块整体显示或隐藏」的分支 | 标「假」的说明这次没测到，补数据 |
| 循环内分支 | 按实际数据行统计真假分布 | 「全部走进」说明缺反例，「从未走进」说明缺正例 |
| 字段对账 | 模版引用了但 JSON 没有 / JSON 有但模版没用 | 确认是不是字段名写错或后端漏下发 |

三类问题的含义：

- **空值风险** — `${xxx}` 或 `#assign` 右侧取不到值又没写 `!默认值`，运行时抛 `InvalidReferenceException`
- **数组越界** — `content[1]` 但实际数据只有 1 项
- **指令闭合** — `<#if>` / `<#list>` 没配对

## 怎么加场景

编辑 `ftl-selftest/scenarios.json`，每个场景是对基线数据的一组增删改：

```json
{
  "name": "无支付信息",
  "expect": "Payment 整块不渲染（含标题与分隔线）",
  "remove": ["tradeInfo"],
  "set": { "orderInfo.orderChannel": 1 }
}
```

`remove` 和 `set` 的路径支持 `a.b.c` 和 `a.b[0].c`。`set` 会自动补建中间层。

加场景的依据来自报告的「用例还缺的顶层分支」章节——它会直接告诉你哪个条件从没为真过。
目标是把该章节清空。

## 判不了的要说判不了

条件里如果调用了自定义 `#function`（比如 `buildOrderBadge` 返回的文案），静态分析给不出结论，
报告会标成「判不了」并单列一节，**不计入覆盖率分母**。

这是工具的能力边界，不是用例没写够。这类分支必须人工看预览或真机确认，
不要因为报告显示「通过」就认为它们被测过了。

## 这套工具测不到的部分

写报告和回复用户时必须如实说明，不能让人误以为跑完就等于验收通过：

- 真实 FreeMarker 引擎的渲染结果（本工具是静态推演）
- 视觉样式：断行、对齐、溢出、弹层位置 —— 用 `ftl-ticket-html-preview` skill 出预览看
- 邮件客户端兼容性（Outlook 用 Word 引擎，Gmail 会剥离 `<style>`）
- 短信通道与短链跳转
- 业务口径是否符合产品预期

## 推荐工作流

```text
改 / 新建 xxx.ftl
  → 改现有模版：node ftl-selftest/run-regression.mjs xxx.ftl data.json   # 引入的问题清零
  → node ftl-selftest/run-suite.mjs xxx.ftl                              # 出自测结论
  → 错误全部修掉，告警逐条确认
  → 报告里「用例还缺的分支」清空（不够就补 scenarios.json）
  → 用 ftl-ticket-html-preview 出预览，人眼看样式
  → 把自测报告贴进 MR 描述
  → 提 MR，人工评审
```

从飞书需求文档一路走到提 MR 的完整链路（含建分支、写 MR 描述），用 `ftl-ticket-workflow` skill。

## 工具自身的可信度

`ftl-selftest/fixtures/broken-ticket.json` 是一份故意做坏的数据，用来验证工具真的会报错、
而不是永远报通过。改动分析逻辑后必须回归这一条：

```bash
node ftl-selftest/run-selftest.mjs <模版.ftl> ftl-selftest/fixtures/broken-ticket.json /tmp/broken.md
# 期望：退出码 1，报出赋值空值风险与数组越界
```

正常数据报通过、坏数据报失败，两头都对了，报告才有意义。

## 禁止

- 跑出错误却在回复里说「基本没问题」
- 把「判不了」当成「测过了」
- 为了让报告好看而放宽检查，或直接删掉报错的用例
- 只贴结论不贴报告路径
- 把报告文件提交进模版仓库——它是过程材料，提 MR 时走 GitLab 附件区上传
