# 需求到 MR · 通用骨架

这个 skill 管的是**流程**，不是某种技术。它的价值不在于把活干得多漂亮，
而在于不许跳步——最容易出事的永远是「我觉得这块没动，不用验了」和
「我以为需求是这个意思」。

领域相关的深度检查靠专门的 skill 接上去（如小票模版用 `ftl-ticket-workflow`），
本骨架只保证流程完整、结论诚实。

## 何时用

- 给了飞书需求文档链接，要求按流程做完并提 MR
- 目标仓库不是小票模版仓（那个走 `ftl-ticket-workflow`，它有 FTL 领域知识）

## 开工前必须问清

**不要猜，猜错了整条链路白跑。** 缺哪项就先问：

1. **目标仓库路径与目标分支** —— 代码落到哪，MR 合向哪
2. **改现有功能还是新增** —— 决定回归范围，这是最关键的分叉
3. **怎么算验证通过** —— 见下一节，先探测，探测不出来就问人

## 一、读需求，落成书面口径

飞书 MCP：`wiki_v2_space_getNode` 拿 obj_token，再 `docx_v1_document_rawContent` 取正文。

读完**不要直接开写**，先把需求翻译成一张改动清单：

| 模块 | 改动 | 涉及文件/接口 | 边界情况的表现 |
|------|------|---------------|----------------|

**最后一列最容易被需求文档略过，也最容易上线出事。** 数据为空、接口失败、
权限不足、超长文案时该显示什么，需求文档很少写全，必须问到没有歧义再动手。

需求文档和设计稿冲突时，**以确认过的口径为准，不要盲跟图**，并把结论记下来。

## 二、编码

改现有代码**先读完整文件**再改，不要凭片段猜上下文。
跟着仓库既有的写法走——命名、注释密度、目录结构，别引入这个仓库没有的风格。

## 三、验证：先探测，别假设

```bash
node workflow/detect-verification.mjs <仓库路径>
```

脚本会读 `package.json` / `Makefile` / `pom.xml` / CI 配置，**按命令内容而非命令名**
分成三类：可安全执行、有副作用勿自动执行、需人工确认。

### 为什么必须读内容

本组前端仓库的 `make test` **不是跑测试**，它把当前分支合进 `test` 分支并 push，
是部署动作。按名字猜会把代码推上共享测试环境。同理 `make mr` 也会推远端。

**只跑探测结果里标为「可安全执行」的命令。** 标为有副作用的，
即使名字再像验证也不要自动执行；需要跑就先问用户。

### 仓库没有测试怎么办

很常见，比如 `posbee-h5-admin` 就只有 lint 和 build、没有单元测试。这时候：

- 跑能跑的（lint、构建、类型检查），把结果如实报出
- **明确写清「本仓库无自动化测试，功能验证是人工做的」**
- 不要用「lint 通过」暗示「功能正确」，这两件事没关系

如果连 lint 和构建都没有，就直说这个仓库没有自动化验证手段，
改动只能靠人工验证和评审兜住。**宁可承认没测，也不要假装测过。**

### 改现有功能要有回归意识

只知道「改完之后没报错」不够，得知道「有没有碰坏原来是好的东西」。
最低限度：改动前先跑一遍验证记下基线，改完再跑，对比差异。

## 四、提 MR

MR **统一用 GitLab 令牌调 API 创建**，见下方命令。

仓库里可能存在 `make mr` 之类的本地提 MR 脚本，**不要执行它们**——
它们会推远端、改分支状态，且产出的 MR 形态不受本流程控制。
探测脚本会把这类命令列进「有副作用」一栏，看到了绕开即可。

令牌放在 `~/.zbspos-gitlab-token`（scope 选 `api`），不要写进任何仓库或聊天记录。

### 分支命名以目标仓库习惯为准

```bash
node gitlab/suggest-branch-name.mjs <仓库路径> <需求名slug> [feature|hotfix]
```

各仓库规范不通用：`print-util` 是 `需求名_日期_作者`，`posbee-h5-admin` 是 `需求名_作者_日期`。
作者段用的是个人代号而非 `git config user.name` 的全名，脚本认不出时**必须问用户**，不要自己编。

### 创建 MR

```bash
node gitlab/gitlab-api.mjs mr-create <项目路径> <源分支> <目标分支> <标题> <正文文件>
node gitlab/gitlab-api.mjs mr-note   <项目路径> <MR编号> <正文文件> [附件路径]
node gitlab/gitlab-api.mjs upload    <项目路径> <文件路径>
```

提交信息用中文，格式 `类型(范围): 说明`。

### MR 正文必须包含

缺一项就是不合格的 MR：

- 飞书需求文档链接
- 改了什么、为什么这么改
- **跑了哪些验证、结果如何**（命令写出来，别只写「已自测」）
- **哪些没验证到**，明确列出留给评审
- 需要评审拍板的口径问题

过程材料（测试报告、截图、构建产物）走 GitLab 附件区上传，
**不要提交进仓库**。提完用 `git diff --name-only <目标分支>..<分支>` 核一遍变更文件。

### 提完 MR 必须提醒用户补跑 make mr

GitLab API 建好 MR 之后，**流程还没完**：组内合入规范通常还要用户本地把分支压成一条 `fetch:[memo]`。

**不要替用户执行 `make mr`。** 它会改写提交历史、切换分支，且 `memo` 必须由用户确认。
Agent 只负责在提完 MR 的回复里提醒，并给出可复制命令。缺这一步视为流程未完成。

提醒模板（按目标仓库替换 memo）：

```markdown
组内合入前请在目标仓库本地执行：

make mr memo=<一句话说明>

这条命令会把当前分支压成 `fetch:[memo]`，不会清掉已用 API 写好的 MR 正文。
压完后推同一条源分支即可，不必新开 MR。
```

`memo` 用需求核心动作写成一句中文，例如 `复制Modifier支持一键清空关联餐品`。
仓库没有 `make mr` 目标时，跳过本步并说明原因。

## 卡住时怎么办

| 卡点 | 处理 |
|------|------|
| 飞书文档读不到 | 换 `docx_builtin_search` 按标题搜；仍失败就请用户贴正文 |
| GitLab 401 | 令牌失效，请用户重新生成 PAT（scope 选 `api`）写入 `~/.zbspos-gitlab-token` |
| GitLab 404（私有仓库） | 通常是无权限而非不存在，先 `whoami` 确认令牌有效 |
| 目标分支受保护 | 合入需 Maintainer，MR 提完要告知用户找谁合 |
| 探测不出验证手段 | 问用户这个仓库平时怎么验证，别自己发明 |
| 需求有歧义 | 停下来问，不要挑一个自己觉得合理的往下做 |

## 禁止

- 跳过验证直接提 MR
- 自动执行被标为「有副作用」的命令，包括 `make mr` 这类本地提 MR 脚本
- 仓库没有测试却在 MR 里暗示「已测试通过」
- 自己编造分支名里的作者代号
- MR 描述只写「已自测」，不写具体跑了什么、什么没测到
- 把测试报告、构建产物提交进业务仓库
- 需求有歧义时自己替产品做决定
