# 小票需求全流程

这个 skill 把散在四处的动作串成一条链：需求在飞书、模版在本地、自测在 `ftl-selftest`、
MR 在内网 GitLab。它的价值不在于某一步做得多好，而在于**不许跳步**——
最容易出事的恰恰是「我觉得这块没动，不用测了」。

## 何时执行

- 用户给了飞书需求文档链接，要求做小票模版
- 用户说「按这套流程走」「飞书需求到 MR 一条龙」
- 已经改完 FTL，要求出报告并提 MR

单纯只想自测、不提 MR 的，直接用 `ftl-selftest` skill 就行，不必走完整流程。

## 开工前必须问清的三件事

**不要猜，猜错了整条链路都白跑。** 缺哪项就先问用户：

1. **目标仓库路径** —— FTL 最终要落到哪个本地仓库的哪个目录
   （已知：`print-util` 放在 `src/main/resources/templates/`）
2. **是改现有模版还是新增** —— 决定要不要做回归对比，这是最关键的分叉
3. **配套 JSON 从哪来** —— 仓库里只有 FTL 没有数据样例，改现有模版时必须让用户提供
   对应的真实 JSON，否则自测只是走过场

## 六个步骤

### 一、读需求，落成书面口径

用飞书 MCP 读文档：`wiki_v2_space_getNode` 拿 obj_token，再 `docx_v1_document_rawContent` 取正文。

读完**不要直接开写**，先把需求翻译成一张改动清单，逐条列出：

| 分区 | 改动 | 数据来源字段 | 无数据时的表现 |
|------|------|--------------|----------------|

「无数据时的表现」这一列最容易被需求文档略过，也最容易上线出事——
是整块隐藏、还是显示占位、还是显示 0，必须跟用户确认到没有歧义再动手。

### 二、编码

新增模版按现有模版的结构写；改现有模版**先读完整文件**再改，不要凭片段猜上下文。

命名参考已落地的 `order-trade-ticket-template.ftl`：按**业务内容**命名，不要带渠道名
（同一份模版会同时用于 H5、短信、邮件）。

### 三、自测

新增模版：

```bash
node ftl-selftest/run-suite.mjs <模版.ftl>
```

改现有模版：**先跑回归，再跑套件**。

```bash
node ftl-selftest/run-regression.mjs <模版.ftl> <数据.json> [基线ref]
```

基线默认 `HEAD`，即「你改之前仓库里的样子」。报告只列差异：

- **本次改动引入的问题** —— 退出码 1 就是这里非空，必须清零才能继续
- **本次改动消除的问题** —— 顺手修好的
- **新增的顶层分支** —— 你这次新加的判断，必须去 `scenarios.json` 补对应用例，
  否则这些新逻辑等于没测

问题指纹按内容而非行号比对，所以代码整体位移不会产生误报；反过来说，
**报出来的就一定是真的新问题**，不要当噪音跳过。

### 四、出预览看样式

```bash
# 用 ftl-ticket-html-preview skill
```

静态分析测不了断行、对齐、溢出。这一步必须做，且要把预览文件路径给用户。

### 五、建分支

分支命名**以目标仓库的历史习惯为准**，不要套用别的仓库的规范——
`print-util` 用 `需求名_日期_作者`，`posbee-h5-admin` 用 `需求名_作者_日期`，两者不通用。

```bash
node gitlab/suggest-branch-name.mjs <仓库路径> <需求名slug> [feature|hotfix]
```

脚本会读该仓库最近的分支统计出真实格式，并列出作者段的实例。
作者段用的是**个人代号**（如 `xiaowh` / `jany` / `wjh`），不是 `git config user.name` 的全名，
脚本认不出你的代号时会要求你确认，此时**必须问用户**，不要自己编一个。

```bash
git -C <仓库路径> checkout main && git -C <仓库路径> pull
git -C <仓库路径> checkout -b <分支名>
```

### 六、提 MR

提交信息用中文，格式 `类型(范围): 说明`，例如 `feat(templates): 新增订单与交易合并的小票模版`。

```bash
node gitlab/gitlab-api.mjs mr-create <项目路径> <源分支> <目标分支> <标题> <正文文件>
```

MR 正文必须包含，缺一项就是不合格的 MR：

- 飞书需求文档链接
- 自测结论：跑了几个场景、错误 0、覆盖率多少
- 改现有模版时附回归对比结论（引入 0 个新问题）
- **静态分析测不到的部分**，明确列出留给评审确认
- 需要评审重点看的业务口径

### 自测报告随 MR 上传，但不入库

`print-util` 是给后端用的模版仓库，自测报告和预览 HTML 是过程材料，**提交进去会污染仓库**。
正确做法是走 GitLab 附件区：文件存在 uploads 空间，评审能点开看，但不产生提交、不进 MR 的变更文件列表。

```bash
# 发一条带附件的评论：正文里的 {{附件}} 会被替换成附件链接
node gitlab/gitlab-api.mjs mr-note <项目路径> <MR编号> <正文文件> [附件路径]

# 只上传拿链接，自己贴到描述里
node gitlab/gitlab-api.mjs upload <项目路径> <文件路径>

# 覆盖 MR 描述
node gitlab/gitlab-api.mjs mr-update <项目路径> <MR编号> <正文文件>
```

配套的两条纪律：

- 生成报告时用第四个参数把输出路径指到**目标仓库外面**，
  否则 `run-regression.mjs` 默认写在模版旁边，也就是写进了目标仓库
- 结论摘要（场景表、错误数、覆盖率）直接写进评论正文，评审不用下载就能看见；
  完整报告和预览 HTML 挂附件

提完 MR 用 `git diff --name-only main..<分支>` 核一遍，变更文件里只该有 `.ftl`。

## 两种情形的差别

| | 新增模版 | 改现有模版 |
|---|---|---|
| 基线数据 | 用户提供的 JSON | 必须要到对应真实 JSON |
| 回归对比 | 不适用（基线里没有这个文件） | **必须做**，退出码必须为 0 |
| 场景用例 | 从零建一套 | 补充新增分支对应的场景 |
| 评审重点 | 整体结构与口径 | 未改动分区有没有被殃及 |

改现有模版时最大的风险是**改 A 影响 B**：模版里共用的 `#function`、`#assign`
被改动后，会波及所有引用它的分区。回归报告里「新增顶层分支」为 0 但问题数变了，
往往就是这种情况，要顺着报告的行号回看。

## 卡住时怎么办

| 卡点 | 处理 |
|------|------|
| 飞书文档读不到 | 换 `docx_builtin_search` 按标题搜；仍失败就请用户贴正文 |
| GitLab 401 | 令牌失效，请用户重新生成 PAT（scope 选 `api`）写入 `~/.zbspos-gitlab-token` |
| GitLab 404（私有仓库） | 通常是无权限而非不存在，先 `whoami` 确认令牌有效 |
| 目标分支受保护 | `main` 受保护，合入需 Maintainer 操作，MR 提完要告知用户找谁合 |
| 没有配套 JSON | 停下来问用户要，不要自己造一份假数据然后报告「测试通过」 |

## 禁止

- 跳过自测直接提 MR
- 改现有模版不做回归对比
- 自己编造分支名里的作者代号
- 自己造 JSON 冒充真实数据出报告
- MR 描述里只写「已自测通过」，不写测不到的部分
- 报告有错误级问题却对用户说「基本没问题」
- 把自测报告、预览 HTML 提交进模版仓库（应走附件区）
